● 可以禁用。USB_RTL8152 是 USB 外接网卡驱动，R3S 的两块板载网口分别由
  R8169（RTL8111H PCIe）和 REALTEK_PHY（RTL8211F PHY）驱动，不依赖它。

  它当初被保留是 trim-r3s.sh 的策略性选择（注释写 "常见 USB
  千兆网卡"），但不是强制依赖。要禁用它，在 trim-r3s.sh 的 A.5.5 段加上
  USB_RTL8152 即可，同时可考虑把 USB_USBNET 框架也一起处理。

  要我帮你加上这个改动吗？

✻ Worked for 24s

❯ USB_USBNET是USB网卡的框架是么？                                               

  Thought for 2s (ctrl+o to expand)

● 是的。USB_USBNET 是 USB 网络适配器的通用框架/核心模块，所有 USB
  网卡驱动（USB_RTL8152、USB_PEGASUS、USB_KAWETH 等）都依赖它。

  当前配置状态：

  CONFIG_USB_RTL8152=m      ← 具体驱动（RTL8152/RTL8153 USB 千兆网卡）
  CONFIG_USB_USBNET=m        ← 框架层（所有 USB 网卡都需要的核心）

  两者的关系是：USB_RTL8152 depends on USB_USBNET。如果 USB_USBNET
  被禁用，USB_RTL8152 自然也无法启用。

  对于 R3S（纯路由器，两个板载 GbE 口），两者都可以安全禁用。要不要我一起处理？

❯ SPI是给Nord Flash提供功能的么？                                               

  Thought for 4s (ctrl+o to expand)

● 不是。SPI 和 NOR Flash 的关系：

  - SPI 是一种通用串行总线协议，能接的设备很多：传感器、GPIO
  扩展芯片、显示屏、Flash 存储等。SPI 是"路"，不是"车"。
  - SPI NOR Flash 需要三层配合：SPI 控制器驱动 → SPI_MEM（内存操作层）→
  MTD_SPI_NOR（NOR Flash 驱动）

  W 轮已经把 Flash
  专用的两层（SPI_MEM、MTD_SPI_NOR、SPI_ROCKCHIP_SFC）全裁掉了，当前保留的只是
  SPI 总线本身：

  SPI=y ── SPI_MASTER=y ── SPI_PL022=y + SPI_ROCKCHIP=y
                                ↑
                      通用 SPI 控制器，GPIO 引脚可接任意 SPI 设备
                      不依赖 SPI_MEM，不走 Flash 路径

  换句话说，现在的 SPI 配置是把"路"留着但不带"运 Flash 的车"——GPIO 上的 SPI
  引脚还能用，但不能接 NOR Flash 了。R3S 从 eMMC 启动也不需要。

  要继续留着还是连 SPI 总线一起裁？

  ┌───────────┬───────────────────────┬──────┐

  └───────────┴───────────────────────┴──────┘

  每次启动内核都会尝试初始化这 4 个不存在的 LSM，虽然不会出错但会在 dmesg

● 不是缺陷。对于专用路由器这种嵌入式场景，MAC LSM 是过度设计，理由：

  路由器不需要 MAC 的原因

  1. 攻击面极小。 路由器只跑内核网络栈 + sing-box + sshd，没有多用户环境、没有
  Web 服务器、没有数据库。传统 DAC（用户/组权限）完全够用。

  2. 行业惯例。 OpenWrt、RouterOS、pfSense 都不启用
  SELinux/AppArmor。嵌入式路由器用最小化服务 + 网络隔离做安全，不靠 MAC。

  3. 性能代价真实。 Cortex-A55 + 2GB RAM 上跑 MAC
  不是免费的——每个文件操作、socket 调用都要过 LSM 钩子。对路由器转发性能有影响。

  4. 真正的安全防线在别处：

  ┌───────────────────────────────┬───────────────┐
  │             防线              │     状态      │
  ├───────────────────────────────┼───────────────┤
  │ nftables/iptables 防火墙      │ ✅ 完整保留   │
  ├───────────────────────────────┼───────────────┤
  │ WireGuard 加密隧道            │ ✅ 完整保留   │
  ├───────────────────────────────┼───────────────┤
  │ VLAN 网络隔离                 │ ✅ 完整保留   │
  ├───────────────────────────────┼───────────────┤
  │ 最小化攻击面（少服务=少漏洞） │ ✅ 编译时已砍 │
  ├───────────────────────────────┼───────────────┤
  │ SSH key-only 认证             │ 部署时配置    │
  ├───────────────────────────────┼───────────────┤
  │ 定期内核/软件更新             │ 运维层面      │
  └───────────────────────────────┴───────────────┘

  5. 被裁掉的是"能力"不是"防线"。 裁掉的 LSM 框架不会引入漏洞，只是去掉了进程级
  强制访问控制这个能力。路由器没有不受信的多用户环境，这个能力本来就用不上。

  ---
  结论：安全上没有缺陷，放心裁。继续上面的 8 组清理？
